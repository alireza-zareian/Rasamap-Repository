# رسامپ

**سامانهٔ جست‌وجو و ثبت آگهی رسانه‌های تبلیغاتی محیطی ایران**

فهرستی یکپارچه و قابل جست‌وجو از ۳٬۵۳۶ بیلبورد، تابلوی پل عابر، استرابورد ایستگاه و
نمایشگر شهری در ۱۰۱ شهر — با نقشه، قیمت، مشخصات فنی و برآورد بازدید روزانه.

`Next.js 16` · `React 19` · `TypeScript strict` · `Prisma 7 + SQLite` · فارسی و راست‌به‌چپ


> ### ⚠️ وضعیت پروژه
>
> این سامانه یک **نمونهٔ کارآمد و در حال اجرا** است، نه محصولی مستقرشده. تا این تاریخ روی هیچ
> دامنهٔ عمومی مستقر نشده و روی رایانهٔ توسعه اجرا می‌شود. بخش‌هایی از آن **عمداً** ساخته
> نشده‌اند (رزرو آنلاین، درگاه پرداخت، خوراک زندهٔ داده) و دلیل هرکدام در مستندات آمده است.
>
> آنچه ساخته شده کار می‌کند و آزموده شده — ۱۱۳ آزمون خودکار، همه موفق. آنچه نشده، فهرست و
> توجیه شده است ([محدودیت‌های شناخته‌شده](#محدودیت‌های-شناخته‌شده))، و مسیر تکمیل آن بدون
> نیاز به بازطراحی روشن است.

## مسئله‌ای که حل می‌کند

بازار رسانهٔ محیطی در ایران پراکنده است. اطلاعات هر سازه نزد مالک یا پیمانکار همان سازه
می‌ماند، پس خریدار تبلیغات برای یافتن یک گزینهٔ مناسب باید جداگانه با چند واسطه تماس
بگیرد و پاسخ‌هایی را که در قالب‌های متفاوت می‌گیرد دستی مقایسه کند. نتیجه، نبودِ یک نمای
واحد از عرضهٔ موجود است.

رسامپ آن نما را می‌سازد. خریدار میان هزاران رسانه جست‌وجو و پالایش می‌کند، موقعیت هر
کدام را روی نقشه می‌بیند، و پس از ورود به حساب کاربری شمارهٔ تماس مالک را می‌گیرد.
صاحبان رسانه هم آگهی خود را از راه یک فرم چندمرحله‌ای ثبت می‌کنند تا پس از بررسی کارشناس
منتشر شود.

> رسامپ مالک رسانه‌ها و واسطهٔ مالی نیست، و به همین دلیل عمداً جریان «رزرو آنلاین»
> ندارد — چیزی که در اختیار ندارد را نمی‌فروشد. استدلال کامل در
> [`docs/engineering-decisions.md`](./docs/engineering-decisions.md) §۱۷.

## چه چیزی این پروژه را از فهرست‌های موجود جدا می‌کند

وب‌گاه‌های امروزی رسانهٔ محیطی در ایران عمدتاً **وب‌گاه یک شرکت‌اند، نه یک بازار**: هر یک
موجودی خودش را نشان می‌دهد و برای هر سازه یک عکس، یک اندازه، یک نام خیابان و گاهی یک قیمت
منتشر می‌کند.

| | وب‌گاه‌های موجود | رسامپ |
|---|---|---|
| **دامنهٔ موجودی** | فقط سازه‌های همان شرکت | تجمیع سه منبع در یک فهرست: **۳٬۵۳۶ رسانه، ۱۰۱ شهر** |
| **جست‌وجوی یکپارچه** | باید چند وب‌گاه را جدا گشت | یک پالایه روی شهر، نوع، قیمت، ابعاد و وجود تصویر |
| **نقشه** | معمولاً فقط نام خیابان به‌صورت متن | فهرست و نقشه کنار هم — **۳٬۰۲۰ رسانه با مختصات (۸۵٪)** |
| **مقایسهٔ کنار هم** | ندارد | انتخاب چند رسانه و مقایسهٔ ستونی مشخصات و قیمت |
| **برآورد بازدید روزانه** | ندارد | **مدل شفاف مبتنی بر کلاس معبر** — پایین‌تر |
| **شفافیت قیمت** | پراکنده، گاهی «تماس بگیرید» | قیمت در خودِ فهرست، قابل مرتب‌سازی و پالایش |
| **ثبت آگهی خودخدمت** | معمولاً تماس تلفنی | فرم چندمرحله‌ای با بارگذاری تصویر و چرخهٔ تأیید |
| **حفاظت از دادهٔ تماس** | شماره در صفحهٔ عمومی | پشت احراز هویت، با ثبت درخواست و سقف نرخ |
| **فارسی و راست‌به‌چپ** | غالباً قالب ترجمه‌شده با ایراد چیدمانی | راست‌به‌چپ بومی در چیدمان، جدول‌ها، نمادها و انیمیشن‌ها |

### نقطهٔ تمایز اصلی — برآورد بازدید روزانه

هیچ‌یک از منابع بررسی‌شده عددی برای «چند نفر در روز این سازه را می‌بینند» منتشر نمی‌کند،
در حالی که این دقیقاً عددی است که خریدار تبلیغات برای سنجش ارزش خرید به آن نیاز دارد.

رسامپ این عدد را از داده‌ای که *موجود است* برآورد می‌کند (کلاس معبر، اندازهٔ سازه، نوع
رسانه و شهر) با پیروی از شکلی که صنعت تبلیغات محیطی جهانی به کار می‌برد
(`Geopath` در آمریکا، `Route` در بریتانیا):

```
vehicles     = roadClassBase × cityFactor
opportunity  = vehicles × occupancy + pedestrians
visibility   = seeRoad × seeType × (1 + sizeBonus)
impressions  = opportunity × visibility
```

سه ویژگی این مدل که آن را از یک عدد دلبخواه جدا می‌کند:

- **پایه‌اش کلاس معبر است، نه جمعیت شهر.** یک بزرگراه در هر شهری ترافیک بزرگراه دارد؛
  جمعیت شهر فقط آن را مقیاس می‌دهد، آن هم زیرخطی (توان ۰٫۳۵).
- **قطعی و بازتولیدپذیر است.** هیچ عدد تصادفی‌ای در کار نیست؛ تنوع لازم از درهم‌سازی
  هویت خودِ رکورد می‌آید که در اجراهای مختلف پایدار است.
- **منبع هر ضریب ثبت شده است.** جمعیت شهرها از سرشماری، ضریب ۱٫۵۵ نفر بر خودرو از ارقام
  شرکت کنترل ترافیک تهران، و لنگرهای قیمت از میانهٔ قیمت‌های منتشرشدهٔ خودِ منابع.

پیاده‌سازی: [`scraper/traffic_formula.py`](./scraper/traffic_formula.py)

## معماری — دو مسیر داده

کل سامانه (رابط کاربری، مسیرهای API و رندر سمت سرور) در یک پایگاه کد است و به‌صورت یک
واحد مستقر می‌شود.

**مسیر ۱ — سرور مستقیم از پایگاه داده می‌خواند.** صفحهٔ جزئیات رسانه یک Server Component
است: هنگام ساخت صفحه، سرور خودش لایهٔ داده را صدا می‌زند و HTML آماده می‌فرستد. یک پرش،
بدون تبدیل به JSON، بدون درخواست شبکهٔ سرور به خودش.

**مسیر ۲ — مرورگر مسیر API را صدا می‌زند.** هر تعامل پس از بارگذاری صفحه (پالایش،
صفحه‌بندی، ثبت آگهی، هر عملیات پنل مدیریت) با `fetch` به `/api/` می‌رود.

هر دو مسیر از **یک لایهٔ داده** (`lib/db/`) عبور می‌کنند: یک منبع حقیقت، بدون منطق تکراری.

> **چرا هر صفحه‌ای مسیر API خودش را صدا نمی‌زند؟** یک API بدونِ رابط کاربری (مثل
> Django + DRF) مانند آشپزخانهٔ ابری است: فقط ارسال بیرون، چون راه دیگری ندارد. رسامپ یک
> رستوران با سرویس بیرون‌بر است — مهمانِ سر میز غذایش را مستقیم از آشپزخانه می‌گیرد، و
> سفارش بیرون‌بر بسته‌بندی می‌شود. آشپزخانه برای هر دو یکی است. مسیر ۱ نه میان‌بر است و نه
> نقص؛ الگوی توصیه‌شدهٔ خودِ Next.js و گزینهٔ سریع‌تر است.
>
> شرح کامل + جدول کارایی: [`docs/architecture.md`](./docs/architecture.md)

## راه‌اندازی

تنها پیش‌نیاز، `Node.js 20` یا بالاتر است. هیچ سرویس بیرونی، پایگاه دادهٔ جداگانه یا
کانتینری لازم نیست.

```bash
npm install                    # postinstall خودش Prisma Client را می‌سازد
cp .env.example .env           # مقادیر را پر کنید
npx prisma migrate deploy      # ساخت پایگاه داده و جدول‌ها
npm run db:seed                # دادهٔ اولیه (~۳۵۰۰ رسانه)
npm run demo                   # build + start → http://localhost:3000
```

متغیرهای لازم (نام‌ها در `.env.example`): `DATABASE_URL`، `AUTH_SECRET` (دست‌کم ۳۲ نویسه)،
`ADMIN_EMAIL`، `ADMIN_PASSWORD_HASH`، `ADMIN_NAME`، و برای لایهٔ نقشه `NESHAN_API_KEY` و
`NEXT_PUBLIC_NESHAN_KEY`. اگر یکی از موارد الزامی نباشد، سرور همان هنگام بالا آمدن با
پیامی روشن متوقف می‌شود ([`lib/env.ts`](./lib/env.ts)) — به‌جای آنکه وسط کار کاربر خراب شود.

حساب‌های آمادهٔ آزمون: [`RUNBOOK.md`](./RUNBOOK.md)
(`npm run db:seed:demo:full`).

### حالت‌های اجرا و انتخاب درست میان آن‌ها

برای مشاهده یا ارائهٔ سامانه پیشنهاد می‌شود از `npm run demo` استفاده شود؛ `npm run dev`
تنها هنگام توسعهٔ کد کاربرد دارد. دلیل این پیشنهاد در ادامه با اندازه‌گیری آمده است.

نکتهٔ مقدماتی: «build» یک حالت اجرا نیست، یک مرحله است. حالت production همان `next start`
است و چیز جداگانه‌ای ندارد.

| دستور | معادل Next | چه می‌کند | سایت بالا می‌آید؟ | کِی |
|---|---|---|---|---|
| `npm run dev` | `next dev` | هر صفحه را لحظهٔ کلیک از صفر کامپایل می‌کند و ۶۷۱۰ فایل را watch می‌کند | ✅ | **فقط** هنگام کدنویسی |
| `npm run build` | `next build` | فقط می‌سازد (خروجی در `.next/`) و تمام می‌شود | ❌ | یک بار پیش از `start` |
| `npm run start` | `next start` | از روی build آماده اجرا می‌کند — همین حالت production است | ✅ | اجرای واقعی (~۱ ثانیه) |
| `npm run demo` | `build && start` | هر دوی بالا پشت سر هم | ✅ | ساده‌ترین راه، بعد از هر تغییر کد |

**اندازه‌گیری واقعی روی همین پروژه**، برای نخستین بازدید از ده مسیر:

| حالت | پردازندهٔ مصرفی |
|---|---|
| `npm run dev` | **۹٫۷ ثانیه** |
| `npm run demo` | **۰٫۱ ثانیه** |

اختلاف حدود **۹۷ برابر** است. علتش روشن است: حالت توسعه هر صفحه را در همان لحظهٔ درخواست
از نو ترجمه می‌کند و هزاران فایل را نیز زیر نظر دارد، در حالی که حالت ساخته‌شده این ترجمه را
یک بار و پیشاپیش انجام داده است. اثر عملی این اختلاف روی یک رایانهٔ همراه بدون خنک‌کنندهٔ
فعال محسوس است، و توصیه می‌شود سامانه پیش از آغاز هر جلسهٔ ارائه ساخته و اجرا شود، نه در
حین آن.

`start` و `demo` از نظر بار پردازشی یکسان‌اند؛ تنها تفاوتشان مرحلهٔ build اولیه است.
شرح کامل و روش اندازه‌گیری: [`docs/engineering-decisions.md`](./docs/engineering-decisions.md) §۲۲.

### دستورها

```bash
npm run demo                # build + start — برای دیدن یا ارائهٔ سایت
npm run start               # اجرا از روی build موجود (حالت production)
npm run dev                 # سرور توسعه — فقط هنگام کدنویسی
npm run build               # فقط ساخت؛ باید بدون خطا پاس شود
npm run lint                # بررسی سبک و خطاهای ایستا
npm test                    # ۱۱۳ آزمون API روی یک ساخت تولیدی
npm run bench               # سنجش کارایی زیر بار

npx prisma migrate deploy   # اعمال مهاجرت‌ها
npm run db:seed             # دادهٔ اولیه
npm run db:seed:demo:full   # حساب‌ها و رکوردهای دمو
npm run db:backup           # نسخهٔ پشتیبان آنلاین SQLite → backups/
npm run db:studio           # Prisma Studio
```

## آزمون

`npm test` یک سرور **تولیدی** روی درگاه ۳۱۰۰ می‌سازد و اجرا می‌کند و پایگاه دادهٔ ایزولهٔ
خودش را از نو می‌سازد. کل اجرا حدود ۱۷٫۶ ثانیه طول می‌کشد.

۱۱۳ آزمون، بدون هیچ وابستگی بیرونی، مستقیم با درخواست HTTP. سرفصل‌ها: اعتبارسنجی ورودی و
فهرست‌های مجاز، کنترل دسترسی در سطح نقش و در سطح شیء، سقف نرخ، **عدم امکان شمارش کاربران
— هم در متن پاسخ و هم در زمان پاسخ**، رد فایلی که ادعای تصویر دارد ولی امضای بایتی تصویر
ندارد، ماشین حالت تأیید آگهی، چرخهٔ رمز یک‌بارمصرف، درستی مرتب‌سازی (با محافظ در برابر
«موفقیت پوچ» روی فهرست خالی)، و نشانه‌گذاری درست کوکی امن پشت پروکسی رمزنگاری‌شده.

## امنیت و صحت — خلاصه

- **پایپلاینِ ثابت روی هر مسیر مدیریتی**: بررسی نشست ← سقف نرخ ← اعتبارسنجی ← منطق
  کسب‌وکار. ترتیب قابل جابه‌جایی نیست: سقف نرخ پیش از احراز هویت یعنی مهاجم بی‌حساب
  می‌تواند سهمیه را تمام کند.
- **اعتبارسنجی طرح‌واره‌ای روی تمام ورودی‌ها** با `.safeParse()`، و فهرست مجاز برای هر
  مقدار مرتب‌سازی و پالایش پیش از رسیدن به پرس‌وجو.
- **مرز دسترسی روی نقطهٔ پایانی، نه در رابط کاربری** — پنهان‌کردن یک دکمه امنیت نیست.
- **نشست**: توکن `HS256` در کوکی `HttpOnly` با `SameSite=Strict`.
- **گذرواژه**: `bcrypt` با ضریب هزینهٔ ۱۲، و مقایسهٔ ساختگی برای شمارهٔ ناموجود تا زمان
  پاسخ لو ندهد کدام شماره ثبت است.
- **یکتایی عملیات**: ثبت آگهی کلید یکتایی دارد؛ تصمیم تأیید تک‌شلیک است؛ ثبت نظر و
  بازمحاسبهٔ میانگین امتیاز در یک تراکنش‌اند.
- **رد ممیزی ماندگار** برای هر تغییر مدیریتی، با شناسهٔ مدیر و نشانی شبکه.
- **مدیریت خطا**: کاربر پیام فارسی و یک شناسهٔ کوتاه می‌بیند؛ رد پشته و جزئیات درونی فقط
  در ثبت رخداد سرور می‌مانند.

## محدودیت‌های شناخته‌شده

فهرست زیر صادقانه است و برای پیش‌گیری از برداشت اغراق‌آمیز آورده می‌شود:

1. **داده زنده نیست.** مجموعهٔ فعلی یک گردآوری نقطه‌ای است؛ خزنده در مخزن هست ولی
   زمان‌بندی‌شده اجرا نمی‌شود.
2. **برآورد بازدید، اندازه‌گیری نیست.** مدل از شکل صنعتی پیروی می‌کند ولی با شمارش میدانی
   اعتبارسنجی نشده است.
3. **یک نمونهٔ اجرایی.** موتور پایگاه داده و سقف نرخ هر دو تک‌نمونه‌ای‌اند؛ مسیر مهاجرت به
   PostgreSQL روشن است (تغییر رشتهٔ اتصال، نه بازنویسی) ولی پیموده نشده.
4. **پوشش آزمون در سطح API است.** رفتار مرورگر دستی آزموده شده، نه خودکار.
5. **پرداخت بیرون از سامانه است.** پلن ویژه با تأیید دستی کارشناس فعال می‌شود.
