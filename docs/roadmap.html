مسئله

بازار تبلیغات محیطی ایران آنلاین نیست. کسی که می‌خواهد بیلبورد اجاره کند باید به آژانس‌ها زنگ بزند، و هیچ جایی نمی‌تواند ببیند در یک شهر چه رسانه‌ای هست، کجاست، چقدر بزرگ است و چقدر می‌ارزد. سایت‌های موجود (IRBillboard، Billboardiha) فهرست‌های ساده‌اند: بدون مقایسه، بدون تخمین بازدید، اغلب بدون قیمت.

رسامپ این بازار را در یک جا جمع می‌کند: داده از پنج منبع جمع‌آوری و یکسان‌سازی می‌شود، کاربر جستجو و فیلتر و مقایسه می‌کند، و برای گرفتن شمارهٔ صاحب رسانه باید حساب بسازد. صاحبان رسانه هم می‌توانند خودشان آگهی ثبت کنند که بعد از بررسی کارشناس منتشر می‌شود.

مدل کسب‌وکار — و چرا «رزرو آنلاین» عمداً وجود ندارد

رسامپ مالک هیچ بیلبوردی نیست، پس نمی‌تواند چیزی را که در اختیار ندارد بفروشد. اگر دکمهٔ «رزرو» می‌گذاشتیم، تعهدی می‌دادیم که پشتوانه‌ای نداشت. به‌جایش: خریدار شمارهٔ صاحب رسانه را می‌گیرد و معامله بیرون از پلتفرم انجام می‌شود؛ درآمد از سمتِ آگهی‌دهنده می‌آید — پلن ویژه که آگهی را بالای نتایج می‌برد.

این یک نقطه‌قوت دفاعی است، نه یک کمبود داور احتمالاً می‌پرسد «چرا رزرو ندارید؟». پاسخ: یک واسطهٔ مالی شدن بدون قرارداد با صاحبان رسانه و بدون درگاه پرداخت، وعدهٔ دروغ است. حذف زیرسیستم رزرو یک تصمیم مهندسی ثبت‌شده است (§۱۷ در docs/engineering-decisions.md)، نه چیزی که از قلم افتاده باشد.

معماری — دو مسیر داده

اولین سؤالی که یک اپ Next.js در جلسهٔ دفاع می‌سازد

سؤالی که حتماً پرسیده می‌شود: «چرا همهٔ صفحه‌ها API را صدا نمی‌زنند؟»

در رسامپ داده از دو مسیر متفاوت به کاربر می‌رسد، و این عمدی است:

مسیر ۱ — صفحه مستقیم از دیتابیس می‌خواند صفحه‌هایی مثل جزئیات بیلبورد یا صفحهٔ اصلی، روی سرور ساخته می‌شوند. همان‌جا مستقیم از دیتابیس می‌خوانند و HTML آماده به مرورگر می‌رود. بدون درخواست شبکهٔ اضافه، بدون حالت «در حال بارگذاری».
مسیر ۲ — مرورگر API را صدا می‌زند هرجا که کاربر تعامل دارد — فیلتر کردن، صفحهٔ بعد، ثبت نظر، گرفتن شماره — مرورگر یک درخواست HTTP به /api/… می‌فرستد و فقط همان تکه را به‌روز می‌کند.
تشبیه رستوران مسیر ۱ مثل این است که آشپز خودش غذا را روی میز بگذارد — آشپزخانه و سالن یک ساختمان‌اند، پس چرا پیک بگیریم؟ مسیر ۲ مثل سفارش گرفتنِ گارسون در وسط غذاست: مشتری چیز تازه‌ای می‌خواهد، باید کسی برود و بیاورد.

این میان‌بر یا نقص نیست. این الگوی رسمی و توصیه‌شدهٔ خودِ Next.js است و از یک API جدا (مثل معماری هدلسِ Django REST) سریع‌تر است، چون یک رفت‌وبرگشت شبکه کمتر دارد. اگر داور بپرسد «پس API شما به چه درد می‌خورد؟» پاسخ: API برای تعامل، برای مصرف‌کنندهٔ بیرونی و برای اپ موبایل آینده است — و همان API است که پنل مدیریت کاملاً روی آن کار می‌کند.

۴.۱ — ثبت‌نام و ورود کاربر accounts

ورود با شمارهٔ موبایل و رمز. رمز با bcrypt (هزینهٔ ۱۲) هش می‌شود و نشست یک JWT امضاشده در کوکی HttpOnly است — یعنی جاوااسکریپت صفحه اصلاً نمی‌تواند آن را بخواند، پس یک حملهٔ XSS هم نمی‌تواند بلیت ورود را بدزدد.

جزئیاتی که ارزش گفتن در دفاع را دارد وقتی شماره‌ای در سیستم نیست، سرور باز هم یک هش bcrypt واقعی را مقایسه می‌کند و بعد خطا می‌دهد. چرا؟ چون اگر این کار را نکند، پاسخ برای «شمارهٔ ناموجود» چند صد میلی‌ثانیه سریع‌تر می‌آید و مهاجم فقط با کرنومتر می‌فهمد کدام شماره ثبت شده است. این باگ واقعاً در پروژه پیدا شد و تستی دارد که زمان پاسخ را می‌سنجد.

MAP-A

«API Key Required» روی نقشه

نقشه مکرراً این پیام را نشان می‌دهد — قبلاً نشان نمی‌داد

⏸ تحقیق معوق
وضعیت فعلی: tile provider فعلی CARTO است (cartocdn.com) — OpenStreetMap-based، بدون API key در URL tile. منشأ پیام «API Key Required» مشخص نیست. ممکن است از جای دیگری بیاید (مثلاً geocoding Neshan، یا تغییر سیاست CARTO).

وظایف تحقیق

⏸
شناسایی دقیق منشأ پیام «API Key Required» — console log، network tab، error boundary
⏸
تشخیص اینکه آیا CARTO سیاست استفاده رایگان را تغییر داده یا origin restriction اضافه کرده
⏸
مقایسه رفتار فعلی با کد/کانفیگ قبلی (git history اگر موجود باشد)
⏸
بررسی آیا مشکل از tile provider است، clustering CDN (unpkg)، یا geocoding
⏸
ارزیابی provider های جایگزین که برای ایران قابل اطمینان هستند — بدون شروع حلقه تعویض بی‌هدف
MAP-B

مختصات بیلبوردها نادرست است

بیلبوردها در شهرها یا مناطق اشتباه نمایش داده می‌شوند

⏸ تحقیق معوق
مشکل: مختصات‌های موجود در DB ممکن است از scraper، geocoding خودکار، یا ورودی دستی باشند. تشخیص «کجای pipeline خطا ایجاد می‌کند» قبل از هر تصحیح لازم است. تصحیح تصادفی مختصات ممنوع است.

وظایف تحقیق

⏸
ردیابی کامل pipeline مختصات: منبع داده → DB → geocoding → provider → frontend → لینک Google Maps
⏸
نمونه‌برداری: چند بیلبورد با مختصات اشتباه شناسایی شود، منشأ lat/lng آنها در DB ردیابی شود
⏸
تعیین اینکه آیا مشکل در داده خام scraper است یا geocoding بعد از scrape
⏸
مقایسه مختصات DB با موقعیت واقعی چند نمونه — تشخیص الگوی خطا (offset ثابت؟ شهر اشتباه؟ تصادفی؟)
MAP-C

لینک «مشاهده در نقشه» / Google Maps نادرست

صفحه جزئیات بیلبورد لینک Google Maps باز می‌کند که گاهی شهر اشتباه است

⏸ تحقیق معوق
مثال: بیلبورد تهران ممکن است لینک Google Maps به ابهر باز کند. دلیل احتمالی: مختصات اشتباه در DB، یا URL با آدرس/نام به جای lat/lng، یا هر دو. قبل از تصحیح URL باید ریشه مشخص شود.

وظایف تحقیق

⏸
بررسی دقیق نحوه تولید URL Google Maps در کد (lat/lng مستقیم؟ آدرس متنی؟ query؟)
⏸
تعیین اینکه آیا مختصات قبل از URL generation اشتباه است (مشکل MAP-B) یا URL generation اشتباه است
⏸
بررسی آیا Google Maps query-based search به جای coordinates باز می‌کند — اگر بله، تغییر به maps.google.com/?q={lat},{lng}
⏸
این فیچر مفید است و باید حفظ شود — فقط بعد از رفع مختصات تصحیح شود
MAP-D

محدودیت‌های provider برای ایران

Neshan گزینه مهمی است ولی انتخاب provider باید بر اساس تحقیق باشد نه حدس

⏸ تحقیق معوق
هشدار: تعویض مکرر provider بدون تحقیق ریشه‌ای منجر به حلقه می‌شود. Neshan API key در env vars موجود است (NESHAN_API_KEY). ولی «چه چیزی» از Neshan استفاده می‌شود باید اول روشن شود.
⏸
بررسی همه جاهایی که NESHAN_API_KEY در کد استفاده می‌شود — geocoding؟ tile؟ search؟
⏸
مقایسه provider ها برای ایران: CARTO (فعلی tile)، Neshan، OSM Nominatim (geocoding)، Google Maps API
⏸
تصمیم provider پس از تحقیق MAP-A، MAP-B، MAP-C — نه قبل از آن

سه اشتباه رایج در پرامپت دادن ۱) «یه گزارش خوب بنویس» — مدل نمی‌داند «خوب» یعنی چه؛ طول، مخاطب و ساختار را بگویید. ۲) ندادن منبع — نتیجه‌اش متنی است که قشنگ است ولی دربارهٔ پروژهٔ شما نیست. ۳) خواستنِ همه‌چیز در یک پرامپت — یک فصل در هر بار. متن بلند، کیفیتش افت می‌کند.
فصل ۱۱

مسیر یادگیری برای دفاع

اگر کد را خودتان ننوشته‌اید، این ترتیب را بروید

خبر خوب داور از شما انتظار ندارد هر خط کد را از حفظ باشید — هیچ‌کس نیست. انتظار دارد بدانید هر چیزی کجاست، چرا آن‌طور ساخته شده، و اگر خراب شود چه می‌شود. این سه چیز یادگرفتنی است، و ترتیب زیر دقیقاً برای همان نوشته شده.

هفت گام، به ترتیب

  • ۱مفهوم «سرور و کلاینت». فصل ۲ همین سند و تشبیه رستوران را بخوانید تا بتوانید بدون نگاه کردن توضیحش دهید. این تنها مفهومی است که حتماً پرسیده می‌شود.
  • ۲مدل داده. ERD فصل ۳ را روی کاغذ بکشید. اگر بتوانید نُه جدول و رابطه‌هایشان را از حفظ بکشید، نیمی از دفاع تمام است.
  • ۳یک مسیر API را کامل بخوانید. پیشنهاد: app/api/billboards/[slug]/contact/route.ts — کوتاه است و هر پنج مرحلهٔ نمودار ۲ را دارد. کامنت‌های انگلیسی‌اش دقیقاً «چرا»ی هر خط را می‌گویند.
  • ۴یک صفحه را بخوانید. app/billboard/[slug]/page.tsx — تا تفاوت «صفحه‌ای که روی سرور ساخته می‌شود» با «تکه‌ای که در مرورگر زنده است» را ببینید.
  • ۵تست‌ها را اجرا کنید و خروجی را ببینید. npm test. اسم هر تست یک جملهٔ انگلیسی است که می‌گوید چه چیزی تضمین می‌شود — این‌ها بهترین فهرستِ «سیستم چه کارهایی را قول داده» هستند.
  • ۶عمداً چیزی را خراب کنید. یک عدد در یک فایل عوض کنید، تست بگیرید، ببینید کدام قرمز می‌شود، بعد برش گردانید. هیچ چیز به اندازهٔ این کار نمی‌فهماند که هر تکه چه‌کاره است.
  • ۷تصمیم‌ها را بخوانید. docs/engineering-decisions.md — ۲۳ تصمیم با دلیل. سؤال‌های «چرا این را انتخاب کردی؟» جوابشان همین‌جاست.

حداقلِ TypeScript که باید بفهمید

لازم نیست برنامه‌نویس شوید. این پنج چیز کافی است تا بتوانید کد را بخوانید و توضیح دهید:

چیزی که می‌بینیدیعنی چه
const x = ...یک مقدار با نام x که دیگر عوض نمی‌شود
function f(a: string): numberتابعی که یک رشته می‌گیرد و یک عدد برمی‌گرداند. علامت‌های بعد از دونقطه «نوع» هستند — همان چیزی که TypeScript را از JavaScript جدا می‌کند.

یک ترفند عملی کامنت‌های داخل کد این پروژه عمداً «چرا» را توضیح می‌دهند نه «چه». مثلاً بالای تابع ثبت سرنخ نوشته شده چرا POST است و نه GET. برای آماده شدن، خواندن کامنت‌ها از خواندن کد سریع‌تر و مفیدتر است.
